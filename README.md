# 不動産オーナーアンケート

不動産をお持ちのユーザーに、**①不動産会社からの連絡をどう感じているか ②どんな情報がほしいか** を
7問で聞く定量アンケート。回答の最後で**30分のオンライン取材（定性）への協力可否**を取り、
協力可の方だけをヒアリング候補にする。`taxnap-survey-tedori` を土台にした単一HTML完結の構成。

- 公開URL: GitHub Pages（Settings > Pages > Branch: `main` / `/root`）
- 回答先: Google スプレッドシート（Google Apps Script 経由）
- 背景: [不動産所得オーナー獲得のための新機能_検討の進め方](https://app.notion.com/p/3d18026138ea819ba2cbca2f72a3a243)

## ファイル

| ファイル | 用途 |
|---|---|
| `index.html` | 本体（単一HTML完結）。設問は `QUESTIONS` |
| `link.html` | 配布リンク作成ページ。配信経路を入れると配布用URLが出る |

## 設問構成（全7問＋取材協力・約2分）

4ブロック構成。**基本情報 → 困りごと → 営業連絡 → データ連携** の順に、答えやすいものから聞く。

| ブロック | # | 設問 | 形式 | 何のために聞くか |
|---|---|---|---|---|
| **A 基本情報** | Q1 | 保有戸数 | 単一6択 | 分類軸。BQの保有状況と突き合わせて回答の妥当性を検証 |
| | Q2 | 物件種別 | 複数選択 | 分類軸。区分マンション保有者を特定 |
| | Q3 | 申告方法 | 単一5択 | 分類軸。ヒアリング対象に「申告方法が異なる方」を混ぜるのに使う |
| **B 困りごと** | Q4 | 不安なこと・気になること | 複数＋その他 | **何を解決すべきか** |
| **C 営業連絡** | Q5 | 連絡の頻度 | 単一5択 | 事実のみ。評価は含めない |
| **D データ連携** | Q6 | 年収をどの粒度で伝えられるか | 単一5択 | **連携の精度の許容度** |
| | Q7 | 借入残高をどの粒度で伝えられるか | 単一5択 | 同上 |
| — | Q8 | 取材協力の可否＋メール | 単一2択＋入力 | 定性への動線。メールはギフト券送付先も兼ねるため**全員必須** |

### Q4 の選択肢（区分ワンルームのメリット3軸を踏まえる）

区分ワンルーム投資のメリットは **インカム / キャピタル / 節税** の3つ。
このうち **インカム（家賃が支出を下回る赤字）はワンルームでは稀**なため設問から外し、
実際の関心である「**いま物件価格がいくらか**」をキャピタル軸として置いた。

**語尾はすべて「〜こと」に統一**している（疑問形と名詞形が混ざると粒度が揃わない）。
1〜2 が「**把握できていないこと**」、3〜5 が「**悪い方向へ変化すること**」の2層構造。

| 選択肢 | 軸 | 層 |
|---|---|---|
| 物件の価格が分からないこと（いまの資産価値・相場） | **キャピタル** | 把握 |
| 節税になっているか分からないこと | **節税** | 把握 |
| 修繕費・管理費が上がること | 費用が上がる | 変化 |
| 金利が上がって返済額が増えること | 費用が上がる | 変化 |
| 空室や家賃下落で収入が減ること | 収入が下がる | 変化 |
| その他（自由記述）／特に不安なことはない（排他） | — | — |

> キャピタルを「下がっていくこと」ではなく「**いくらになっているか分からないこと**」と
> したのは、下落不安だけでなく**含み益を確認したい**という前向きな関心も拾うため。

### Q6・Q7 の設計（連携の「粒度」を聞く）

**「渡すか否か」ではなく「どの粒度なら渡せるか」を聞く。**

営業が年収・借入残高を欲しがる理由は「**新しくローンを組めるかどうかの判断**」
（3者座組設計 §3.5「営業（買い増し）: 年収・借入残高・所得」）。
この目的には**必ずしも生値は要らない**。社内設計も「借入残高レンジ（250万円刻み）・
年1回更新」を想定しており、**この粒度がどこまで許容されるかが実装の分岐点**になる。

場面説明（Q6 に固定で表示）:

> ご自身の状況に合った物件が出たときに、担当の方からご紹介が届く——という仕組みを
> 考えています。新しくローンを組めるかどうかの目安になるため、**年に1回、確定申告の
> あとに**お伝えするとしたら、どの程度までなら差し支えないでしょうか。
> ※ 実際にお伝えするかは、この場で決まるものではありません

選択肢（両問共通の5段階。**具体値 → 幅 → 変動の有無 → 受動 → 拒否**）:

| 段階 | 年収 | 借入残高 |
|---|---|---|
| ① 具体的な金額まで | 例: 780万円 | 例: 1,850万円 |
| ② おおよその幅なら | 例: 700万〜800万円 | 例: 1,800万〜1,900万円 |
| ③ 変動の有無だけ | 増えたか・変わらないか | 減ったか・変わらないか |
| ④ 聞かれたときに自分から | 自動では伝えない | 自動では伝えない |
| ⑤ 伝えたくない | — | — |

この作りにした理由:

- **年収と借入残高を別々に聞く。** 社内設計では「年収・所得・税額は**常に非開示**、
  借入残高のみレンジで任意オプトイン」と分けている。束ねて聞くと年収への抵抗が
  借入残高の判断を汚染し、実態が測れない。
- **「頻度」は場面説明に固定する。** 「年に1回」を前提として固定し、粒度だけを聞く。
  粒度と頻度を同時に聞くと答えにくくなる。
- **④「聞かれたときに自分から」を置く。** 自動連携は嫌でも、相談時なら渡してよい層を
  拾う。ここが多ければ**プッシュ型ではなく相談起点の設計**になる。
- **見返り（自分に合った物件の紹介）と目的（ローンが組めるかの判断）を明示する。**
  何のために渡すのか分からなければ、許容度は測れない。
- **申告データから分かる情報は選択肢に置かない。** 連携の起点が確定申告データである以上、
  「申告が終わったか」「不動産の収支」は渡す情報ではなく**渡した結果分かること**。

### 設問設計で意図的にしていること

- **「特にない」「気にならない」を必ず同格で置く。** 困っていないという事実も拾う。
- **事実 → 評価 の順。** Q5（実際の頻度）で事実を押さえる。
- **Q4 は「知りたいこと」ではなく「不安なこと」を聞く。** 目的は課題解決であり、
  情報ニーズは手段に過ぎない。
- **Q6・Q7 は「抵抗はありますか」と聞かない。** そう聞けば大半が「抵抗あり」になる。
  「**どの程度ならお伝えしてもよいか**」と聞き、どちらにも誘導しない。

### 結果の読み方（事前に決めておく）

| 結果 | 判断 |
|---|---|
| Q4 で節税・物件価格が上位 | タックスナップの申告データで解ける領域。**そのまま実装へ** |
| Q4 で空室・家賃下落が上位 | 賃貸経営の課題。申告アプリでは応えられず、**連携の設計から見直し** |
| **Q7 で「幅なら」以上が過半** | 社内設計（残高レンジ250万円刻み）が**成立**。そのまま実装へ |
| Q7 で「変動の有無だけ」が上位 | レンジすら重い。**増減フラグのみ**に縮小 |
| Q6・Q7 で「聞かれたときに自分から」が上位 | 自動連携をやめ、**相談起点**の設計へ |
| Q6・Q7 で「伝えたくない」が過半 | 連携の前提が崩れる。**申告機能単体で価値を出す設計へ** |
| Q6 ≪ Q7（年収は渋いが残高は出す） | 社内設計の想定どおり。**年収は非開示のまま進める** |

## 配布のしかた（URLパラメータ）

**HTMLは1つ。配信経路はURLで渡す。**

```
https://txto-inc.github.io/taxnap-survey-fudosan/?c=mail   ← メール配信
https://txto-inc.github.io/taxnap-survey-fudosan/?c=line   ← LINE配信
https://txto-inc.github.io/taxnap-survey-fudosan/?c=push   ← アプリ内通知
```

| パラメータ | 値 | 効果 |
|---|---|---|
| `c` | 配信コード（**集計キー**） | シートの「配信経路」「配信コード」列に記録 |
| `n` | 表示名（省略時は `CHANNELS` の登録名） | 同上 |

パラメータなしでも動く（`direct` として記録）。`link.html` を開くと配布用URLを生成できる。

> `c` は集計キーなので**一度配ったら変えない**こと（別の経路として集計される）。

## 配信対象（2026-09-11 時点）

BigQuery（2025年分）で「不動産所得を申告し、貸付不動産の保有状況を入力済み」のユーザーは **444名**。
内訳は下表。**区分マンション2〜3戸にあたる層は94名**（うち給与所得も申告しているのは64名）。

| 建物戸数 | 人数 | うち給与併記 |
|---|---|---|
| 0戸（土地・駐車場のみ） | 45 | 16 |
| 1戸 | 239 | 135 |
| 2戸 | 56 | 39 |
| 3戸 | 38 | 25 |
| 4〜5戸 | 32 | 20 |
| 6戸以上 | 34 | 17 |

> 戸数は「貸付不動産の保有状況」の**建物のみ**（住宅用・住宅用以外の棟数＋室数）。土地・駐車場は含まない。
> Q1・Q2 の自己申告とこの数字を突き合わせれば、回答の妥当性を検証できる。

### ヒアリングに進むかの判断

回答者のうち**区分マンション保有が30%以上かつ実数20名以上**なら、当初計画どおり3名にヒアリングする。
それ未満なら定量結果だけで判断するか、対象を1戸まで広げる。

## 回答データ

`回答` シートに1行ずつ追記される（列は `gas/Code.gs` の `COLUMNS`）。
複数選択は `, ` 区切りの文字列で入る。

## GASデプロイ手順

1. スプレッドシートを作り、**拡張機能 > Apps Script** で `gas/Code.gs` を貼る
2. **プロジェクトの設定 > スクリプト プロパティ** に `POST_TOKEN` を登録
   （`index.html` の `POST_TOKEN` と同じ文字列にする。既定値 `taxnap_fudosan_CHANGE_ME` は必ず変更する）
3. **デプロイ > 新しいデプロイ > 種類=ウェブアプリ**
   - 次のユーザーとして実行: **自分**
   - アクセスできるユーザー: **全員**
4. 発行された `/exec` URL を `index.html` の `GAS_URL` に貼る

> `GAS_URL` が空のあいだは送信をスキップし、コンソールに payload を出すだけになる（画面は最後まで通る）。
> 到達確認は `/exec` をブラウザで開く（現在の回答数が出る）か、スプレッドシートの行を見る。

## 元にしたリポジトリとの違い

`taxnap-survey-tedori` は手取り試算が主目的のため、税額計算エンジン・グラフ・金額入力を持つ。
本リポはそれらを**すべて外し**、選択式の設問と送信だけに絞っている。
UI（配色・スライド遷移・選択肢の作法）と GAS の受け口は踏襲しているので、
`QUESTIONS` を差し替えれば別テーマのアンケートにも転用できる。
