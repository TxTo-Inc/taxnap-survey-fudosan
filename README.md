# 不動産オーナーアンケート

不動産をお持ちのユーザーに、**①購入後の営業連絡で何が嬉しかったか ②買い増しのために
どこで物件を探しているか ③紹介の精度を上げるために確定申告データを出してよいか** を
9問で聞く定量アンケート。回答の最後で**30分のオンライン取材（定性）への協力可否**を取り、
協力可の方だけをヒアリング候補にする。`taxnap-survey-tedori` を土台にした単一HTML完結の構成。

**ユーザーの行動（嬉しかった連絡 → 買い増し意向 → リサーチ → 使っているメディア → その優位性）ごとに
設問を分け、「この機能にニーズがあるのはこういう人だ」をクロス集計で絞り込む**設計にしている。

- 公開URL: GitHub Pages（Settings > Pages > Branch: `main` / `/root`）
- 回答先: Google スプレッドシート（Google Apps Script 経由）
- 背景: [不動産所得オーナー獲得のための新機能_検討の進め方](https://app.notion.com/p/3d18026138ea819ba2cbca2f72a3a243)

## このアンケートで明らかにすること（ゴール）

| # | ゴール | 対応する設問 |
|---|---|---|
| ① | 購入**後**の営業連絡で、オーナーは**何にありがたみを感じているのか** | **Q3** |
| ② | 買い増しを考える人は、**どこで・どうやって物件を探しているのか** | **Q4〜Q7** |
| ③ | **紹介の精度を上げるため**なら、確定申告データを出してよいと思うか | **Q8・Q9** |
| ④ | ③をOKとする場合、**どの粒度なら問題ないか** | **Q8・Q9**（5段階） |

**設計の軸は「ユーザーの行動ごとに分ける」こと。**
嬉しかった連絡 → 買い増し意向 → リサーチ行動 → 使っているメディア → その優位性 → データ提供、
という**行動の連鎖**で並べ、どの行動をしている人がこの機能にニーズを持つのかを、
クロス集計で事後に絞り込めるようにしている。

### 購入「後」に限定している理由

**購入前の物件相談については聞かない。** 購入前の相談は誰にとってもありがたいもので、
「ありがたい」と答えさせるだけの設問になり、ニーズの強弱が測れない。
差が出るのは購入後（＝物件を買ったあと、担当者との関係がどうなっているか）なので、
Q3 はそこに限定している。

### 「どう感じるか」の5段階評価を置いていない理由

かつては Q3 で総合評価（ありがたい〜一切不要の5段階）、Q4 で具体例、と2問に分けていたが、
**評価と具体例を並べて聞くと両方が甘くなる。** 先に評価で「ありがたい」と答えた人は、
自分の回答と整合させようとして具体例でも肯定を選びやすくなる（逆も同じ）。

**実際に嬉しかった連絡を挙げてもらえば、選択数がそのまま満足度の代理指標になる。**
ゼロ個（「特に思い当たることはない」）なら購入後の連絡に価値を感じていない、
3つ以上なら関係が機能している、と読める。評価を別途聞く必要がない。

### Q3 の選択肢の作り（ゴール①）

**確定申告・税金を先頭に置く。** タックスナップが解ける領域なので、
ここが上位に来るかどうかが、申告データを軸にした機能の前提になる。

**「自分に合った物件の紹介」を置く。** ③で検証する体験そのもの。
ここが既に嬉しかったと答える人は、データ連携の受け入れ余地が大きいと読める。

**「特に思い当たることはない」を必ず置く。** ここが過半なら、購入後の連絡に
価値を感じておらず**データ提供の動機もない**（＝座組みの前提から見直し）と読む。

### Q4 の分岐（買い増し意向がない人は Q5〜Q7 を飛ばす）

Q4 で **「購入する考えはない」「むしろ売却を考えている」** を選んだ方には、
リサーチ行動の設問（Q5〜Q7）を出さず、**Q8 へ直行**する。

探していない人に「どのメディアを重宝しているか」を聞いても答えようがなく、
「特にない」を3問続けて選ばせることになり離脱を招く。

- 分岐の定義は `QUESTIONS.q4_intent` の `skipResearch:true`。選択肢を増減しても
  フラグを立てるだけで分岐が付いてくる（画面IDの直書きをしていない）
- 進捗バーの分母も実際に通る画面数に合わせて変わる（分岐時は 7、通常は 10）
- **Q8・Q9 は意向にかかわらず全員に聞く。** 買い増しを考えていない層の許容度と
  比較したいため（意向のある人だけが出してよいと答えるのか、それとも意向と無関係か）
- Q5〜Q7 に答えた後で Q4 を「購入する考えはない」に変更した場合は、
  Q5〜Q7 の回答を破棄する（`clearResearchAnswers()`）。通らなかった画面の回答が
  送信されると集計が汚れるため。スキップした行は `Q5-Q7スキップ` 列で識別できる

### 絵文字の使い分け

**Q1〜Q2（属性質問）は絵文字あり、Q3以降（判断を要する設問）は絵文字なし。**

前半は事実を答えるだけなので、絵文字があると視認性が上がり選びやすくなる
（特に Q1 の戸数は数字絵文字が効く）。
後半は連絡への評価やデータ提供の可否を判断する設問で、絵文字が内容と
一対一で対応しないため、視線を奪うノイズになり判断を妨げる。

### 話題の転換（Q3・Q4）

話題が変わる箇所に、**Q番号の直後・設問タイトルより前**で緑背景の見出しを置く。
設問の後に置くと「設問を読んでから前提を知る」ことになり、読み返しが必要になる。

| 位置 | 転換 | 文言 |
|---|---|---|
| Q3 | 自分の物件 → 担当者の話 | **物件を購入された不動産会社の担当の方**についてお伺いします |
| Q4 | 担当者 → 今後の購入の話 | **今後の物件のご購入**についてお伺いします |

**Q3 の「物件を購入された」を省略しない。** 今回の対象は管理委託済みのオーナーが多く、
接点のある担当者が複数いるため、管理会社の担当と取り違えるリスクがある。

### Q6・Q7 の設計（メディアとその優位性）

**Q6 にはポータルだけでなく「担当営業からの紹介」「知人・オーナー仲間」も置く。**
ポータルサイトだけを並べると、「担当営業が情報源」という実態を答えられなくなる。
ここで担当営業が上位に来るなら、③のデータ連携は既存の行動の延長線上にある。

**Q7 に「自分に合う物件が出てくる」を必ず置く。**
ここが上位なら、確定申告データによる紹介精度の向上が刺さる層がいることになる。
逆に「物件数が多い」「新着が早い」が支配的なら、精度より網羅性・速度の勝負であり、
データ連携の訴求は弱い。**Q7 は③の訴求が成立するかの判定に直結する。**

**理由は5つに絞る**（物件数 / 新着 / 自分に合う / 非公開物件 / 情報の正確さ）。
「収支シミュレーションができる」は楽待・健美家の機能で、ポータル利用者だけに偏る。
「見やすい・使いやすい」はどのサービスにも当てはまり差が出ない。
いずれも③の判定に効かないため落とした。**軸は物件供給（量・速さ・精度・希少性）と
情報の信頼性**に揃えている。

### Q8・Q9 の設計（連携の「粒度」を聞く）

**「渡すか否か」ではなく「どの粒度なら渡せるか」を聞く。**

営業が年収・借入残高を欲しがる理由は「**新しくローンを組めるかどうかの判断**」
（3者座組設計 §3.5「営業（買い増し）: 年収・借入残高・所得」）。
この目的には**必ずしも生値は要らない**。社内設計も「借入残高レンジ（250万円刻み）・
年1回更新」を想定しており、**この粒度がどこまで許容されるかが実装の分岐点**になる。

場面説明（Q8 に固定で表示。選択肢が画面外に押し出されないよう補足は3行に抑えている）:

**タイトル**（何のための仕組みかを示す）
> ご自身に合う物件だけが届くようご紹介の精度を上げるため、
> 確定申告の年収が担当営業に連携される仕組みを検討しています

**サブタイトル**（何を答えるかを示す。**設問文そのものなので黒字**）
> どの程度までならお伝えしてもよいと思われますか？

**補足**
> 連携は**年1回・3月末ごろ**を想定しています。
> ※ 事前に合意をした方のみ、連携される仕組みを想定しています
> ※ 実際にお伝えするかは、この場で決まるものではありません

> **目的を先・仕組みを後に置く。** 「年収が連携される仕組み」から読ませると、
> 何のために渡すのか分からないまま身構えることになる。「自分に合う物件だけが届くよう
> 精度を上げるため」を先に置くと、見返りを理解した状態で粒度を判断できる。
>
> **見返りを「紹介の精度」に接続する。** 直前の Q6・Q7 で「どのメディアを・なぜ重宝しているか」
> を答えた直後なので、「精度が上がる」が何を指すのかが具体的に伝わる状態になっている。
> 単に「物件の紹介が届く」と書くより、Q7 で答えた優位性と地続きになる。
>
> **タイトルに目的が入ったぶん、補足は頻度と前提だけにする。** 補足にも
> 「精度を上げるため」を残すと同じ文が2回出て、読み飛ばされる。
>
> **タイトルに手動の改行を入れない。** 幅を決め打ちすると狭い画面で不自然に折れる。
> `word-break:auto-phrase` に任せて文節で折り返させる。
>
> **「事前に合意をした方のみ」を明記する。** これがないと勝手に送られる仕組みと
> 読まれ、拒否方向に振れる。
>
> **Q9 は Q8 と全く同じ文言構造にする**（「年収」を「借入残高」に置き換えるだけ）。
> Q9 を「同じ仕組みで」と省略形にすると、Q8 を覚えている前提になり、
> 前提条件（合意した方のみ・年1回・この場では決まらない）が Q9 で伝わらない。
> 冗長に見えても、両方を独立して読める形にする。

選択肢（両問共通の5段階。**具体値 → 幅 → 変動の有無 → 受動 → 拒否**）:

| 段階 | 年収（Q8） | 借入残高（Q9） |
|---|---|---|
| ① 具体的な金額まで | 例: 780万円 | 例: 1,850万円 |
| ② おおよその幅なら | 例: 700万〜800万円 | 例: 1,800万〜1,900万円 |
| ③ 変動の有無だけ | 増えたか・変わらないか | 減ったか・変わらないか |
| ④ 聞かれたときに自分から | 自動では伝えない | 自動では伝えない |
| ⑤ 伝えたくない | — | — |

この作りにした理由:

- **年収と借入残高を別々に聞く（Q8 / Q9）。** 社内設計では「年収・所得・税額は**常に非開示**、
  借入残高のみレンジで任意オプトイン」と分けている。束ねて聞くと年収への抵抗が
  借入残高の判断を汚染し、実態が測れない。
- **「頻度」は場面説明に固定する。** 「年に1回」を前提として固定し、粒度だけを聞く。
  粒度と頻度を同時に聞くと答えにくくなる。
- **④「聞かれたときに自分から」を置く。** 自動連携は嫌でも、相談時なら渡してよい層を
  拾う。ここが多ければ**プッシュ型ではなく相談起点の設計**になる。
- **申告データから分かる情報は選択肢に置かない。** 連携の起点が確定申告データである以上、
  「申告が終わったか」「不動産の収支」は渡す情報ではなく**渡した結果分かること**。

### 設問設計で意図的にしていること

- **「特にない」「特に思い当たることはない」を必ず同格で置く。** 困っていない・
  思い当たらないという事実も拾う。
- **「その他」は排他項目（「特にない」）より後ろに置く。** 自由記述欄が「その他」の
  直下に出るようにするため。間に別の選択肢が挟まると、何に対する記入欄か分からなくなる。
- **Q8・Q9 は「抵抗はありますか」と聞かない。** そう聞けば大半が「抵抗あり」になる。
  「**どの程度ならお伝えしてもよいか**」と聞き、どちらにも誘導しない。

### クロス集計で見たいこと

**「この機能にニーズがある人はこういう人だ」を、行動の組み合わせで絞り込む。**

| 仮説 | 見方 |
|---|---|
| **買い増し意向が強い人ほど、データを渡してよいと思う** | Q4 × Q8・Q9 |
| **自分でリサーチしている人ほど、精度向上に価値を感じて渡す** | Q5 × Q8・Q9 |
| **「自分に合う物件が出てくる」を優位性に挙げた人は、データを渡す** | Q7「自分に合う物件」× Q8・Q9 |
| **担当営業を情報源にしている人は、連携への抵抗が少ない** | Q6「担当営業からの紹介」× Q8・Q9 |
| **申告の説明で助けられた人は、申告データの提供に抵抗が少ない** | Q3「確定申告・税金」× Q8・Q9 |
| **既に物件紹介を嬉しいと感じている人は、連携に前向きか** | Q3「自分に合った物件の紹介」× Q8・Q9 |
| 嬉しかった連絡が多い人ほど、データを渡してよいと思う | Q3の選択数 × Q8・Q9 |
| 買い増し意向がない層でも、データを渡してよいと思うか | Q4「考えはない」× Q8・Q9 |

> 3〜4番目が重要。**「メディアに精度を求めている人」と「データを渡してよい人」が
> 重なるなら、機能の訴求軸は精度で確定する。** 重ならないなら、精度以外の便益
> （手間の削減など）を探すことになる。
>
> **Q3の選択数は満足度の代理指標として使う。** 0個＝購入後の関係が機能していない、
> 3個以上＝機能している。5段階評価を別途聞かなくても、ここで層が切れる。

### 結果の読み方（事前に決めておく）

| 結果 | 判断 |

| Q7 で「物件数が多い」「新着が早い」が支配的 | 精度より網羅性・速度の勝負。**データ連携の訴求を組み直す** |
| **Q6 で「担当営業からの紹介」が上位** | 連携は既存行動の延長。**そのまま実装へ** |
| Q6 でポータルが支配的・担当営業が下位 | 担当営業は情報源として期待されていない。**連携先の前提から見直し** |
| **Q4 で買い増し意向あり（上位3つ）が過半** | 対象市場が成立。**そのまま実装へ** |
| Q4 で「考えはない＋売却」が過半 | 買い増し前提の機能は刺さらない。**申告機能単体で価値を出す設計へ** |
| **Q3 で「確定申告・税金についての説明」が上位** | タックスナップが解ける領域。**そのまま実装へ** |
| **Q3 で「自分に合った物件の紹介」が上位** | ③の体験が既に歓迎されている。**連携の受け入れ余地が大きい** |
| **Q3 で「特に思い当たることはない」が過半** | 購入後の連絡に価値を感じていない＝**データ提供の動機もない**。座組みの前提から見直し |
| Q3 で入居者・修繕が上位 | 賃貸経営の課題。申告アプリでは応えられず、**連携の設計から見直し** |
| **Q9 で「幅なら」以上が過半** | 社内設計（残高レンジ250万円刻み）が**成立**。そのまま実装へ |
| Q9 で「変動の有無だけ」が上位 | レンジすら重い。**増減フラグのみ**に縮小 |
| Q8・Q9 で「聞かれたときに自分から」が上位 | 自動連携をやめ、**相談起点**の設計へ |
| Q8・Q9 で「伝えたくない」が過半 | 連携の前提が崩れる。**申告機能単体で価値を出す設計へ** |
| Q8 ≪ Q9（年収は渋いが残高は出す） | 社内設計の想定どおり。**年収は非開示のまま進める** |

## 配布のしかた（URLパラメータ）

**HTMLは1つ。配信経路はURLで渡す。**

```
https://txto-inc.github.io/taxnap-survey-fudosan/?c=mail   ← メール配信
https://txto-inc.github.io/taxnap-survey-fudosan/?c=line   ← LINE配信
https://txto-inc.github.io/taxnap-survey-fudosan/?c=push   ← アプリ内通知
```

| パラメータ | 値 | 効果 |
|---|---|---|
| `c` | 配信コード（**集計キー**） | シートの「配信経路」「配信コード」列に記録 |
| `n` | 表示名（省略時は `CHANNELS` の登録名） | 同上 |

パラメータなしでも動く（`direct` として記録）。`link.html` を開くと配布用URLを生成できる。

> `c` は集計キーなので**一度配ったら変えない**こと（別の経路として集計される）。

## 配信対象（2026-09-11 時点）

BigQuery（2025年分）で「不動産所得を申告し、貸付不動産の保有状況を入力済み」のユーザーは **444名**。
内訳は下表。**区分マンション2〜3戸にあたる層は94名**（うち給与所得も申告しているのは64名）。

| 建物戸数 | 人数 | うち給与併記 |
|---|---|---|
| 0戸（土地・駐車場のみ） | 45 | 16 |
| 1戸 | 239 | 135 |
| 2戸 | 56 | 39 |
| 3戸 | 38 | 25 |
| 4〜5戸 | 32 | 20 |
| 6戸以上 | 34 | 17 |

> 戸数は「貸付不動産の保有状況」の**建物のみ**（住宅用・住宅用以外の棟数＋室数）。土地・駐車場は含まない。
> Q1・Q2 の自己申告とこの数字を突き合わせれば、回答の妥当性を検証できる。
>
> **Q1 の選択肢は 0戸／1／2／3／4／5戸以上の6択。** 上表は BQ 側が「4〜5戸」「6戸以上」で
> 区切られているため、突合の際は BQ の 5戸・6戸以上を Q1 の「5戸以上」に寄せて比較する
> （上表の 4〜5戸 32名 は 4戸と 5戸に分かれる）。

### ヒアリングに進むかの判断

回答者のうち**区分マンション保有が30%以上かつ実数20名以上**なら、当初計画どおり3名にヒアリングする。
それ未満なら定量結果だけで判断するか、対象を1戸まで広げる。

## 回答データ

`回答` シートに1行ずつ追記される（列は `gas/Code.gs` の `COLUMNS`）。
複数選択は `, ` 区切りの文字列で入る。

分岐でスキップされた Q5〜Q7 は**空欄**で入る（「特にない」と区別できる）。
スキップした行は `Q5-Q7スキップ` 列に `スキップ` が入るので、集計時の母数はここで切る。

> **設問を増減したら `gas/Code.gs` の `COLUMNS` も直す。** ヘッダー行は既存シートでは
> 自動で張り替わらない（1列目の見出しが変わったときだけ書き換わる）。列を足した場合は
> シートの見出し行を手で消すか、新しいシートに切り替える。

## GASデプロイ手順

1. スプレッドシートを作り、**拡張機能 > Apps Script** で `gas/Code.gs` を貼る
2. **プロジェクトの設定 > スクリプト プロパティ** に `POST_TOKEN` を登録
   （`index.html` の `POST_TOKEN` と同じ文字列にする。既定値 `taxnap_fudosan_CHANGE_ME` は必ず変更する）
3. **デプロイ > 新しいデプロイ > 種類=ウェブアプリ**
   - 次のユーザーとして実行: **自分**
   - アクセスできるユーザー: **全員**
4. 発行された `/exec` URL を `index.html` の `GAS_URL` に貼る

> `GAS_URL` が空のあいだは送信をスキップし、コンソールに payload を出すだけになる（画面は最後まで通る）。
> 到達確認は `/exec` をブラウザで開く（現在の回答数が出る）か、スプレッドシートの行を見る。

## 元にしたリポジトリとの違い

`taxnap-survey-tedori` は手取り試算が主目的のため、税額計算エンジン・グラフ・金額入力を持つ。
本リポはそれらを**すべて外し**、選択式の設問と送信だけに絞っている。
UI（配色・スライド遷移・選択肢の作法）と GAS の受け口は踏襲しているので、
`QUESTIONS` を差し替えれば別テーマのアンケートにも転用できる。
