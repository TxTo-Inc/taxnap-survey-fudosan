# 不動産オーナーアンケート

不動産をお持ちのユーザーに、**①不動産会社からの連絡をどう感じているか ②どんな情報がほしいか** を
7問で聞く定量アンケート。回答の最後で**30分のオンライン取材（定性）への協力可否**を取り、
協力可の方だけをヒアリング候補にする。`taxnap-survey-tedori` を土台にした単一HTML完結の構成。

- 公開URL: GitHub Pages（Settings > Pages > Branch: `main` / `/root`）
- 回答先: Google スプレッドシート（Google Apps Script 経由）
- 背景: [不動産所得オーナー獲得のための新機能_検討の進め方](https://app.notion.com/p/3d18026138ea819ba2cbca2f72a3a243)

## ファイル

| ファイル | 用途 |

## 設問構成（全8問＋取材協力・約3分）

4ブロック構成。**基本情報 → 困りごと → 営業連絡 → データ連携** の順に、答えやすいものから聞く。

| ブロック | # | 設問 | 形式 | 何のために聞くか |
|---|---|---|---|---|
| **A 基本情報** | Q1 | 保有戸数 | 単一6択 | 分類軸。BQの保有状況と突き合わせて回答の妥当性を検証 |
| | Q2 | 物件種別 | 複数選択 | 分類軸。区分マンション保有者を特定 |
| | Q3 | 申告方法 | 単一5択 | 分類軸。ヒアリング対象に「申告方法が異なる方」を混ぜるのに使う |
| **B 困りごと** | Q4 | 不安なこと・気になること | 複数＋その他 | **何を解決すべきか**。収支/費用増/収入減の3軸 |
| **C 営業連絡** | Q5 | 連絡の頻度 | 単一5択 | 事実のみ。評価は含めない |
| | Q6 | どんな連絡なら受け取ってよいか | 複数選択 | **連携する情報の中身**。Q4の困りごとに対応させている |
| | Q7 | 連絡で気になる点 | 複数選択 | **拒否の理由**を手段/頻度/中身/不足/送り主に分解 |
| **D データ連携** | Q8 | 担当に伝えてよい情報 | 複数選択 | **連携の可否そのもの**。情報の種類ごとに許容度を測る |
| — | Q9 | 取材協力の可否＋メール | 単一2択＋入力 | 定性への動線。メールはギフト券送付先も兼ねるため**全員必須** |

### 設問設計で意図的にしていること

検証したい論点（連絡は迷惑か／どんな情報がほしいか／データを渡せるか）は
**いずれも聞き方で答えが変わる**ため、Notion の基本方針（§4）に沿って次の作りにしている。

**共通**
- **「特にない」「気にならない」を必ず同格で置く。** 困っていない・気にしていないという事実も拾う。
- **事実 → 選好 → 理由 の順。** Q5（実際の頻度）を先に置き、評価はその後。

**Q4（困りごと）**
- 「知りたいこと」ではなく「**不安なこと**」を聞く。目的は課題解決であり、情報ニーズは手段に過ぎない。
- 買い増し・売却・資産価値は**関心事ではあるが困りごとではない**ので外した。

**Q6（どんな連絡ならよいか）**
- 「迷惑か」の一次元ではなく、**中身の選好**を測る。「内容による」で終わらせない。
- **「新しい物件の紹介」は最後に置く**（Notion §4「新物件を先に見せない」）。先頭に置くと営業提案への誘導になる。
- **「質問したときの回答だけでよい」を入れている。** プッシュ不要・プル希望の層を拾うため。ここが多ければ設計は通知型ではなく相談窓口型になる。

**Q7（気になる点）**
- 「営業連絡が嫌」の正体を**手段（電話）/ 頻度 / 中身（売り込み）/ 不足 / 送り主**に分解する。どれが原因かで打ち手が全く変わるため、切り分けないと結果を使えない。
- **「必要な連絡が来ない」を入れている。** 連絡は過多だけでなく**不足も問題**かもしれない。
- Q5 で「まったく来ない」を選んだ人には**聞かない**（自動で「連絡が来ていない」を記録して Q8 へ）。来ていない連絡について答えさせると実態のない回答が混ざる。

**Q8（データ連携）**
- **「抵抗はありますか」と聞かない。** 年収と借入残高を並べて抵抗を聞けば大半が「抵抗あり」になる。「**伝えてもよいと思えるもの**」と聞き、どちらにも誘導しない。
- **情報の種類ごとに聞く。** 社内設計では「年収・所得・税額は常に非開示、借入残高のみレンジで任意オプトイン」と分けている。束ねて聞くと年収への抵抗が借入残高の判断を汚染する。
- 「物件購入時に年収を提出したと思いますが」と**前置きする。** 既に一度渡した事実を思い出させることで、過度に警戒した回答を防ぐ。
- 「**この場で決まるものではない**」と明記する（Notion §5「実際の共有許諾を決めるものではない」）。

### 結果の読み方（事前に決めておく）

| 結果 | 判断 |
|---|---|
| Q4 で収支・節税が上位 | タックスナップ単体で解ける領域。**そのまま実装へ** |
| Q4 で空室・家賃下落が上位 | 賃貸経営の課題。申告アプリでは応えられず、**連携の設計から見直し** |
| Q6 で「受け取りたくない」が過半 | 情報連携の前提が崩れる。**座組みから見直し** |
| Q6 で困りごと対応型が上位 | **連携の中身が確定。**そのまま実装へ |
| Q6 で「質問したときの回答だけ」が上位 | プッシュ型をやめ、**相談窓口型**に設計変更 |
| Q7 で「電話が困る」が上位 | 手段の問題。**アプリ内通知に寄せれば解決**（最も good news） |
| Q7 で「売り込みが多い」が上位 | 中身の問題。**誰が送るか**の再設計 |
| Q8 で「どれも伝えたくない」が過半 | 連携の前提が崩れる。**申告機能単体で価値を出す設計へ** |
| Q8 で「申告が終わったか」のみ許容 | 連携は**完了フラグのみ**に縮小 |

## 配布のしかた（URLパラメータ）

**HTMLは1つ。配信経路はURLで渡す。**

```
https://txto-inc.github.io/taxnap-survey-fudosan/?c=mail   ← メール配信
https://txto-inc.github.io/taxnap-survey-fudosan/?c=line   ← LINE配信
https://txto-inc.github.io/taxnap-survey-fudosan/?c=push   ← アプリ内通知
```

| パラメータ | 値 | 効果 |
|---|---|---|
| `c` | 配信コード（**集計キー**） | シートの「配信経路」「配信コード」列に記録 |
| `n` | 表示名（省略時は `CHANNELS` の登録名） | 同上 |

パラメータなしでも動く（`direct` として記録）。`link.html` を開くと配布用URLを生成できる。

> `c` は集計キーなので**一度配ったら変えない**こと（別の経路として集計される）。

## 配信対象（2026-09-11 時点）

BigQuery（2025年分）で「不動産所得を申告し、貸付不動産の保有状況を入力済み」のユーザーは **444名**。
内訳は下表。**区分マンション2〜3戸にあたる層は94名**（うち給与所得も申告しているのは64名）。

| 建物戸数 | 人数 | うち給与併記 |
|---|---|---|
| 0戸（土地・駐車場のみ） | 45 | 16 |
| 1戸 | 239 | 135 |
| 2戸 | 56 | 39 |
| 3戸 | 38 | 25 |
| 4〜5戸 | 32 | 20 |
| 6戸以上 | 34 | 17 |

> 戸数は「貸付不動産の保有状況」の**建物のみ**（住宅用・住宅用以外の棟数＋室数）。土地・駐車場は含まない。
> Q1・Q2 の自己申告とこの数字を突き合わせれば、回答の妥当性を検証できる。

### ヒアリングに進むかの判断

回答者のうち**区分マンション保有が30%以上かつ実数20名以上**なら、当初計画どおり3名にヒアリングする。
それ未満なら定量結果だけで判断するか、対象を1戸まで広げる。

## 回答データ

`回答` シートに1行ずつ追記される（列は `gas/Code.gs` の `COLUMNS`）。
複数選択は `, ` 区切りの文字列で入る。

## GASデプロイ手順

1. スプレッドシートを作り、**拡張機能 > Apps Script** で `gas/Code.gs` を貼る
2. **プロジェクトの設定 > スクリプト プロパティ** に `POST_TOKEN` を登録
   （`index.html` の `POST_TOKEN` と同じ文字列にする。既定値 `taxnap_fudosan_CHANGE_ME` は必ず変更する）
3. **デプロイ > 新しいデプロイ > 種類=ウェブアプリ**
   - 次のユーザーとして実行: **自分**
   - アクセスできるユーザー: **全員**
4. 発行された `/exec` URL を `index.html` の `GAS_URL` に貼る

> `GAS_URL` が空のあいだは送信をスキップし、コンソールに payload を出すだけになる（画面は最後まで通る）。
> 到達確認は `/exec` をブラウザで開く（現在の回答数が出る）か、スプレッドシートの行を見る。

## 元にしたリポジトリとの違い

`taxnap-survey-tedori` は手取り試算が主目的のため、税額計算エンジン・グラフ・金額入力を持つ。
本リポはそれらを**すべて外し**、選択式の設問と送信だけに絞っている。
UI（配色・スライド遷移・選択肢の作法）と GAS の受け口は踏襲しているので、
`QUESTIONS` を差し替えれば別テーマのアンケートにも転用できる。
